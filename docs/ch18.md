# Ch 18 — Capstone and mapping the mocks to a real cell (week 12)

Goal: run the complete system as one project, measure it, and know exactly which parts you would replace on a real cell. After this chapter you can read a production palletizing system's architecture and place every component.

## Capstone: a 50-box shift

1. Reset the world. Feed `ABCABCABCA…` (50 boxes) and run `palletize mixed` until the planner reports the pallet full; record the bag.
2. Run `depalletize mixed` on the result with `fail_every_n 7` and `drop_after_s 3.0` injected.
3. From the executive log, compute per-stage times, boxes per minute, retries per box, and time lost to recovery. `tools/job_stats.py` in the companion repository does it from a saved log.
4. Write a one-page report: numbers, the two biggest time sinks, what you would change first.

Typical first results in the VM: 20–30 s per box, dominated by OMPL planning time and the 0.5 m/s velocity scaling; both are knobs you set in Ch 7.

## Mock → real

| Mock (this tutorial) | Real cell | What stays identical |
| --- | --- | --- |
| `mock_components/GenericSystem` | `ur_robot_driver` (or another vendor driver) with the real IP; scaled JTC | URDF, controllers YAML, MoveIt config, every client |
| `mock_camera` | the camera vendor's ROS 2 driver, triggered capture, `PointCloud2` in the optical frame | `box_detector`, `/detections` |
| URDF camera pose | hand–eye calibration: move a target with the robot, fit the camera pose; 1–2 mm residual is good | `camera_optical_frame` name and the TF lookup |
| `mock_gripper` | vacuum ejector on a digital output, vacuum switch on an input (PLC, Modbus TCP, EtherNet/IP) | `SetSuction` service, `/gripper/vacuum` |
| `mock_conveyor` | PLC-controlled belt, photo-eyes, barcode scanner or WMS message | `/photo_eye`, `/conveyor/sku`, `index_out`, `feed_in` |
| `world_model` | reality | nothing: it is deleted |
| SKU table in code | WMS / host system interface (box dims, order, destination) | `matchSku`, the plans |
| Box height from the ring | WMS dims, a light curtain or height sensor after lift, or a scale | `planPick` re-centering |
| `settle()` | physics: stability margins matter; support ≥ 70 % is a common floor | `bestPlacement` |
| Detector on an ideal top view | the same height-map approach works; add side-face points, missing-data handling and a learned fallback for unusual packaging | the height map |

## What a vendor controller does differently

A dedicated palletizing controller, such as the kind Mujin ships, replaces three of your packages with one tightly integrated planner: environment model, collision checking and trajectory generation run in one process, optimized for cycle time, with vendor robot controllers driven directly. The vocabulary you now own maps one to one: planning scene ↔ environment state, `PickPlace` stages ↔ approach/grasp/depart segments, pattern and height map ↔ placement planning, the executive ↔ the task state machine. The debugging skills transfer too: frames first, then the scene, then the planner, then the hardware.

## Go deeper: the two procedures a real cell adds

**Hand-eye calibration.** MoveIt's [hand-eye calibration tutorial](https://moveit.picknik.ai/main/doc/examples/hand_eye_calibration/hand_eye_calibration_tutorial.html) uses the `moveit_calibration` RViz panel: print a ChArUco target, publish images and `CameraInfo` from the camera, record a handful of robot poses, and the panel solves the camera pose (eye-to-hand for our fixed camera, eye-in-hand for an on-arm one). Zivid documents the same procedure for its cameras in its [production preparation guide](https://support.zivid.com/en/latest/camera/academy/applications/depalletization/prepare-for-production.html), together with camera warm-up and in-field verification. The result replaces the `camera_link` origin in `cell.urdf.xacro`; nothing else in the tutorial changes.

**The vendor path for the robot.** The [UR custom workcell tutorial](https://docs.universal-robots.com/Universal_Robots_ROS2_Documentation/doc/ur_tutorials/my_robot_cell/doc/index.html) is the exact recipe: keep `cell_description`, add a control package that includes `ur_ros2_control`, start `ur_control.launch.py` with your description, and run the MoveIt config from Ch 6 next to it. For a non-UR robot, the equivalent is the vendor's ros2_control hardware plugin or one you write ([writing a hardware component](https://docs.ros.org/en/jazzy/p/hardware_interface/doc/writing_new_hardware_component.html)).
